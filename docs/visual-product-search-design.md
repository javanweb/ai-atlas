# جستجوی محصول با تصویر — Atlas Visual Product Search
### سند طراحی و پیاده‌سازی (نسخه ۱)

> ماژول مستقل «جستجوی بصری محصول» برای فروشگاه هایپر صنعت اطلس.
> ورودی: عکس قطعه. خروجی: همان محصول در کاتالوگ، یا محصولات مشابه، یا پیشنهاد ساخت/تأمین سفارشی.

---

## ۱) اصل حاکم بر سیستم

> **«بهتر است محصولی پیدا نشود، تا اینکه محصول اشتباه معرفی شود.»**

تصمیم‌های سیستم فقط و فقط بر پایه‌ی **ظاهر بصری** گرفته می‌شود:
شکل، فرم، هندسه، نسبت ابعاد، ساختار، اجزای قابل مشاهده و ویژگی‌های شاخص.
هیچ‌یک از موارد زیر در تصمیم‌گیری دخالت ندارند:

- نام فایل (`IMG_001.jpg` و `product-final-7.jpg` و `abc123.png` دقیقاً یکسان پردازش می‌شوند)
- EXIF / متادیتا / تاریخ / GPS / مدل دوربین
- متن داخل تصویر یا برچسب کالا
- مشخصات فنی دستی، کد فنی، دسته‌بندی یا قیمت
- جستجوی متنی

## ۲) معماری (Pipeline)

```
عکس کاربر
   │
   ▼ ۱. اعتبارسنجی ورودی           server/visualSearch/routes.ts  (حجم ≤ ۱۲MB، نوع تصویر)
   │
   ▼ ۲. پیش‌پردازش ملایم            imagePreprocess.ts
   │      • رمزگشایی پیکسل‌ها (بدون استفاده از نام فایل)
   │      • تشخیص جسم اصلی + کادر آن  (multiple objects → جسم غالب)
   │      • «وضعیت کانونی» جسم: نرمال‌سازی ملایم نور، تعادل رنگ،
   │        چرخش محور اصلی، قاب‌بندی متقارن، خنثی‌سازی پس‌زمینه
   │
   ▼ ۳. استخراج ویژگی بصری          visualEncoder.ts
   │      • بردار ۵۱۲ بُعدی برای ۴ «نما»: full / object / object-rot180 / object-flip
   │        (HOG چندسطحی + شبکه‌ی رنگ + هیستوگرام شدت + پروفایل سایه‌نما
   │         + امضای شعاعی شکل + ممان‌های شکل + تراکم لبه چندمقیاسه)
   │      • امضای ساختاری (نسبت ابعاد، پرشدگی، سوراخ‌ها، تقارن، اجزا)
   │      • هش ادراکی dHash ۲۵۶ بیتی / pHash ۶۴ / aHash ۶۴ (روی جسمِ کانونی)
   │
   ▼ ۴. جستجوی برداری              vectorStore.ts
   │      • بازیابی «بهترین بردار هر محصول» از کل کاتالوگ (بدون برش زودهنگام)
   │      • گروه‌بندی بر اساس Product ID  (چند تصویر از یک محصول = یک نتیجه)
   │
   ▼ ۵. بازرتبه‌بندی بصری (Re-ranking)   searchEngine.ts + verifier.ts
   │      • ترکیب سه سیگنال مستقل: بردار + ساختار هندسی + هش ادراکی
   │      • پرسش داخلی: «آیا این همان محصول است؟» (نه «آیا شبیه است؟»)
   │
   ▼ ۶. تصمیم سه‌حالته            EXACT | SIMILAR | NO_MATCH
   │
   ▼ ۷. نمایش فارسی بدون اصطلاح فنی و بدون درصد شباهت
```

مسیرهای فرانت‌اند:

- صفحه‌ی کاربر: `/visual-search` → `src/pages/VisualSearchPage.tsx`
- تجربه‌ی جستجو: `src/components/visual-search/VisualSearchExperience.tsx`
- پنل مدیریت: `/admin/visual-search` → `src/admin/modules/VisualSearchModule.tsx`

## ۳) مدل داده

```
Product {
  id, name, sku, category, description, product_url, main_image,
  gallery_images[], stock, price, custom_order_available
}

ProductImage {            // هر محصول می‌تواند چند تصویر داشته باشد
  id, product_id, image_url, embedding, image_type, created_at
}
```

همه‌ی تصاویر یک محصول به **همان Product ID** متصل‌اند؛ بنابراین اگر مشتری از
زاویه‌ی دیگری عکس بگیرد، باز هم همان محصول پیدا می‌شود.

پیاده‌سازی فعلی: `catalog.ts` محصولات را از `src/data/catalogSummary.json`
(۸۶۴ کالا، SKU به شکل `AT-E###`) می‌سازد و برای هر تصویر ۴ بردار ذخیره می‌کند
→ مجموعاً ۳۴۵۶ بردار.

## ۴) پایگاه داده‌ی برداری (قابل تعویض)

رابط مشترک `VectorStore` (در `types.ts`) سه پیاده‌سازی دارد:

| پیاده‌سازی | کلاس | کاربرد |
|---|---|---|
| فایل JSON | `JsonVectorStore` | پیش‌فرض محیط توسعه/تولید سبک (flush اتمیک ۱.۵ ثانیه‌ای) |
| حافظه | `InMemoryVectorStore` | تست‌ها |
| Qdrant | `QdrantVectorStore` | مقیاس میلیونی، جستجوی نزدیک‌ترین همسایه، فیلتر متادیتا |

انتخاب از طریق متغیر محیطی:

```
VISUAL_SEARCH_VECTOR_STORE = json | qdrant | memory
QDRANT_URL / QDRANT_API_KEY / QDRANT_COLLECTION
```

هر بردار متادیتای `productId, imagePath, imageType, view` را همراه دارد؛
بنابراین **گروه‌بندی نتایج بر اساس Product ID** و **فیلتر متادیتا** در هر سه
پیاده‌سازی ممکن است و تعویض پایگاه داده نیازی به بازنویسی سیستم ندارد.

بردارها به‌صورت Int8 + Base64 ذخیره می‌شوند (نسبت به Float32، حدود ۴ برابر
کم‌حجم‌تر) و شباهت با کسینوسی نرمال‌شده محاسبه می‌شود.

## ۵) چرخه‌ی ایندکس‌سازی

- **ایندکس‌سازی دسته‌ای (Batch)**: `POST /api/visual-search/index/reindex`
  (پارامتر `{reset:true}` برای ساخت کامل از صفر).
- **ایندکس‌سازی خودکار**: `startAutoIndexWatch(10min)` هر ۱۰ دقیقه تغییرات
  کاتالوگ را بررسی و فقط تصاویر جدید/تغییریافته را ایندکس می‌کند.
- **تصویر جدید برای محصول موجود**: `POST /index/product/:id/images`
- **تغییر تصویر**: هش تصویر در `imageHashes` تغییر می‌کند →
  بردارهای قبلی همان تصویر حذف و مجدداً تولید می‌شوند.
- **حذف محصول**: `DELETE /index/product/:id` → همه‌ی بردارهای آن حذف می‌شوند.
- **نسخه‌بندی ایندکس**: `INDEX_VERSION` در `indexManager.ts`. با هر تغییر در
  الگوریتم استخراج ویژگی، نسخه بالا می‌رود و در زمان راه‌اندازی، ایندکس
  قدیمی/ناقص به‌صورت خودکار بازسازی کامل می‌شود (بدون دخالت اپراتور).
- **قفل ایندکس**: تا وقتی ساخت در جریان است، درخواست ایندکس‌سازی جدید با
  کد `409` رد می‌شود تا داده‌ها نیمه‌ساخته نشوند.
- **امضای هر نما** به‌صورت جداگانه در `signatures.signatures.json` کش می‌شود
  (کلید `${productId}::${view}`) تا فرآیند ثابت (deterministic) و تکرارپذیر بماند.

## ۶) منطق تصمیم‌گیری

### ۶-۱. سه سیگنال مستقل

| سیگنال | توضیح | چرا لازم است |
|---|---|---|
| `vectorScore` | شباهت کسینوسی بردار ۵۱۲ بُعدی (بهترین جفت از ۴×۴ نما) | تطابق کلی ظاهر |
| `structureScore` | انطباق ساختاری (نسبت ابعاد، پرشدگی، سوراخ‌ها، تقارن، سایه‌نما) | هندسه‌ی قطعه |
| `hashSimilarity` | ۱ − فاصله‌ی ترکیبی dHash/pHash روی «جسم کانونی» | تمایز کالاهای هم‌خانواده (اشباع نمی‌شود) |

امتیاز نهایی:

```
combined = 0.32·vector + 0.34·structure + 0.34·hash
```

> شباهت برداری روی کاتالوگ‌های صنعتی هم‌خانواده به اشباع می‌رسد (۰.۹۷ برای
> کالای درست و کالای اشتباه)، در حالی که ساختار و هش قدرت تفکیک واقعی دارند.
> وزن‌ها با هارنس کالیبراسیون (`scripts/visualSearchTune.mjs`, `scripts/visualSearchEval.mjs`)
> تنظیم و از طریق `VISUAL_SEARCH_WEIGHTS="v,s,h"` قابل بازتنظیم‌اند.

### ۶-۲. شرط‌های پذیرش EXACT

خروجی EXACT تنها زمانی صادر می‌شود که **همه‌ی** شرایط زیر برقرار باشند:

1. `dHash ≤ 16` و `pHash ≤ 5` و `aHash ≤ 5` (تصویرِ جسم، واقعاً همان تصویر)
2. `structureScore ≥ 0.86`
3. تنها **یک** محصول مدعی تطابق قطعی باشد (گارد ابهام؛ اگر دو کالای متفاوت
   تصویر یکسانی داشته باشند، ادعای EXACT رد می‌شود)
4. **گارد حاشیه**: کالای هم‌خانواده‌ی نزدیکی وجود نداشته باشد؛
   `فاصله‌ی برنده ≤ ۰.۵۵ × فاصله‌ی رقیب` یا رقیب به‌قدر کافی دور باشد.

در غیر این صورت: `SIMILAR` (۳ تا ۶ کالای نزدیک، مرتب‌شده بر اساس شباهت بصری)
و اگر هیچ کالایی از کف امتیاز عبور نکند: `NO_MATCH` + فرم ساخت/تأمین سفارشی.

به کاربر نهایی **هیچ‌گاه درصد یا امتیاز شباهت** نشان داده نمی‌شود؛ امتیازها فقط
در پاسخ داخلی/پنل مدیریت و لاگ‌های کالیبراسیون وجود دارند.

## ۷) مقاوم‌سازی (Robustness)

| چالش | راهکار پیاده‌شده |
|---|---|
| پس‌زمینه‌ی متفاوت (میز کار، کارگاه) | تشخیص جسم + خنثی‌سازی پس‌زمینه + حذف نوارهای سراسری (لبه‌ی میز/پس‌زمینه‌ی کاتالوگ) |
| نور متفاوت / سایه | تقسیم بر روشنایی محلی (بدون کشش کنتراست که جزئیات را نابود می‌کند) |
| زاویه و چرخش | «وضعیت کانونی» بر پایه‌ی محور اصلی (ممان‌های مرتبه‌ی دوم) + نماهای rot180/flip |
| فاصله و اندازه‌ی متفاوت | کادربرداری از جسم + قاب‌بندی متقارن با حفظ نسبت ابعاد |
| کیفیت پایین / عکس موبایل | نرمال‌سازی ملایم، حذف نویز مؤثر در بازنمونه‌برداری، آستانه‌های کالیبره |
| چند شیء در تصویر | `detectMainObject` جسم غالب را انتخاب می‌کند |
| نام فایل | هرگز خوانده/ارسال نمی‌شود (سرور فقط Buffer پیکسل می‌گیرد) |
| EXIF | فقط برای «تصحیح نمایش» چرخش؛ هرگز به‌عنوان سیگنال تطبیق |

## ۸) رابط کاربری

صفحه‌ی `/visual-search`:

- عنوان بخش: «محصول موردنظر خود را با تصویر پیدا کنید»
- توضیح: «عکس قطعه یا محصول را آپلود کنید تا در کاتالوگ Atlas جستجو کنیم.»
- دکمه‌ی «آپلود تصویر» + کشیدن‌ورهاکردن (Drag & Drop) + «گرفتن عکس با دوربین» در موبایل
- متن بارگذاری: «در حال بررسی تصویر و جستجو در محصولات...» (چهار مرحله‌ی گویا)
- بدون هیچ اصطلاح فنی (Embedding / Vector / Similarity Score / AI Confidence)

نتیجه‌ها:

- **EXACT** → «محصول موردنظر شما پیدا شد» + تصویر، نام، کد فنی، لینک صفحه‌ی محصول،
  دکمه‌ی «مشاهده محصول» و (در صورت وجود) «استعلام قیمت». **بدون** فهرست مشابه‌ها و **بدون** درصد.
- **SIMILAR** → «محصول دقیق موردنظر شما پیدا نشد، اما محصولات مشابه زیر را پیدا کردیم.»
  + ۳ تا ۶ کالای نزدیک با تصویر، نام، کد، لینک و دکمه‌ی مشاهده/استعلام.
- **NO_MATCH** → «محصول موردنظر شما در کاتالوگ ما پیدا نشد.» +
  «در صورت نیاز، امکان بررسی ساخت یا تأمین محصول موردنظر شما به‌صورت سفارشی وجود دارد.»
  + دکمه‌ی «درخواست ساخت / تأمین سفارشی» → فرم (تصویر قطعه، شرح، تعداد، نام، تلفن،
  شرکت، توضیحات) → ثبت در پنل مدیریت.

## ۹) پنل مدیریت

`/admin/visual-search` با چهار زبانه:

1. **وضعیت**: تعداد محصولات دارای بردار، تعداد تصاویر پردازش‌شده، تصاویر بدون
   بردار، خطاهای پردازش، زمان آخرین ایندکس‌سازی، وضعیت پایگاه داده‌ی برداری،
   دکمه‌ی «ایندکس مجدد محصولات».
2. **درخواست‌های سفارشی**: صندوق ورودی با وضعیت‌های
   جدید / در حال بررسی / امکان ساخت / امکان تأمین / نیاز به اطلاعات بیشتر / بسته‌شده
3. **لاگ جستجوها**: هر جستجو با نوع نتیجه، کاندیداها، زمان پاسخ (بدون نمایش به کاربر نهایی)
4. **تنظیمات**: کف امتیازها، تعداد نتایج مشابه، فعال/غیرفعال بودن بازبینی هوشمند

**آزمون خودکار `GET /self-test?sample=6`:** ۶ از ۶ مورد EXACT — میانگین ۴۷۰ تا ۶۳۰ میلی‌ثانیه برای هر جستجو.

**هارنس `scripts/visualSearchEval.mjs 8`** (۷ کالای نمونه × ۹ تبدیل؛
ستون «EXACT(اشتباه)» یعنی معرفی کالای نادرست به‌عنوان همان قطعه):

|---|---|---|---|---|---|
| تصویر کاتالوگ (بازذخیره) | ۷/۷ | ۷/۷ | ۷/۷ | **۷/۷** | ۰ |
| چرخش ۹۰ درجه | ۷/۷ | ۷/۷ | ۷/۷ | ۶/۷ | ۰ |
| آینه‌ی افقی | ۷/۷ | ۷/۷ | ۷/۷ | ۶/۷ | ۰ |
| کیفیت پایین | ۷/۷ | ۷/۷ | ۷/۷ | **۷/۷** | ۰ |
| روشن‌تر | ۷/۷ | ۷/۷ | ۷/۷ | ۵/۷ | ۰ |
| تیره‌تر | ۷/۷ | ۷/۷ | ۷/۷ | **۷/۷** | ۰ |

| پس‌زمینه‌ی متفاوت + مقیاس کوچک | ۰/۷ | ۰/۷ | ۰/۷ | ۰ | ۰ |
| چرخش ۲۵ درجه روی پس‌زمینه‌ی روشن | ۲/۷ | ۳/۷ | ۳/۷ | ۰ | ۰ |

**تست مقاوم‌سازی (`scripts/visualSearchRobustnessTest.mjs`، ۵ کالا × ۷ تبدیل + تست منفی):**
نرخ تطابق دقیق ۲۱ از ۳۵ (پایه‌ی اولیه: ۱۱ از ۳۵) و **صفر** مورد «معرفی محصول اشتباه به‌عنوان همان قطعه».

**تست منفی** (پس‌زمینه‌ی یکدست، دایره، مستطیل، متن، نویز): همه `NO_MATCH` ✅ — هیچ‌گاه EXACT.

> نکته‌ی مهم برای بهره‌برداری: در موارد «پس‌زمینه‌ی متفاوت + جسم کوچک» محصول
> درست به فهرست کاندیداها نمی‌رسد و سیستم به‌جای پیشنهاد محصول اشتباه،
> `NO_MATCH` (یا در حالت چرخش، SIMILAR کنترل‌شده) برمی‌گرداند — دقیقاً مطابق
> اصل «بهتر است پیدا نشود تا اشتباه معرفی شود».

## ۱۲) محدودیت‌ها و مسیر ارتقا

- استخراج ویژگی فعلی **کاملاً محلی و آفلاین** است (بدون وابستگی به سرویس بیرونی،
  بدون هزینه‌ی API، سازگار با حریم خصوصی) و روی کاتالوگ فعلی اطلس — که تصاویر
  آن پس‌زمینه‌ی یکسان و جزئیات کم دارند — عملکرد خوبی در تشخیص «تصویر یکسان/
  تقریباً یکسان» دارد.
- برای «عکس واقعی از قطعه با پس‌زمینه‌ی پیچیده» (میز کار، سایه، زاویه‌ی دلخواه)
  معماری آماده‌ی تعویض موتور است: افزودن یک ارائه‌دهنده‌ی بردار عمیق
  (مثل DINOv2/CLIP یا Gemini Embedding) در `embeddingProviders.ts` و بالا بردن
  `INDEX_VERSION` — بدون تغییر در UI، پنل مدیریت، فرم سفارش یا منطق تصمیم.
- برای مقیاس میلیونی: `VISUAL_SEARCH_VECTOR_STORE=qdrant` و ایندکس برداری واقعی.

### خارج از دامنه‌ی نسخه ۱ (طبق نقشه راه)
جستجوی متن+تصویر، جستجوی چندتصویری، تشخیص دسته/برند/مدل، قطعات مشابه صنعتی،
اتصال به ERP/انبار/قیمت/CRM.
